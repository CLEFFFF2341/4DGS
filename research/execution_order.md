## 推荐第一批

建议授权 **P00 + 阶段1 + P99**，上限46 GPU小时（含P00、共享缓存、方法smoke、51行正式实验），额外实现错误修复只能在单独预留的12小时总槽中消费，整个项目累计≤220小时。可先仅P00并根据实际统计成本决定是否放行阶段1；这不是要求Astra逐方案回合。

固定基模只用beef；其余场景阶段2才处理。P00完成会给出真实显存/速度/可运行能力表。此文件不授权本轮Astra运行GPU。

## 顺序与可跳过依赖

1. P00：冻结manifest、全保留/加载/评测、K0→K1→K2→K3；K4是CPU派生模块；K5/K6按需实现。P00核心IO/评测失败时所有正式实验停止，P99仍可汇总。
2. P01 → P02 → P03：先确定简单贡献、单删强基线与时间聚合上限。
3. P04 → P05 → P06 → P07 → P08 → P09 → P10：集合覆盖/代表性、时间风险、重估、联合删除、恢复、重现。依赖缺失不阻塞独立项。
4. P11 → P12 → P13：学习mask、容量分配、合并；P11编译失败允许继续P12/P13。
5. P14 → P15 → P16 → P17 → P18 → P19 → P20：类型、轨迹、活动区间、成本、属性。若K2/K3阻塞，P15/P16/P17可在核心IO通过后立即提前执行；P14需K1但不需K2；P20需K1/ray颜色但不需K2单删。
6. P99阶段1汇总→在预设规则内选≤6晋级方案→阶段2（仅用户已授权扩展批次时）→P99→选≤3候选→冻结阶段3→一次最终test→P99最终版。

## 自动批次规则

- 只有一个GPU进程；统计/训练/评测同样串行。CPU文档/汇总可与GPU运行共存，但禁止另开训练。不得生成多个Sol任务争同一GPU。
- 每个任务开始前读取progress.json、检查输入hash与预算余量；已完成同hash行直接复用；新hash另目录，不覆盖。
- 一行失败：保存命令/traceback/峰值/最后checkpoint，分类并做一次规定的诊断/修复；耗尽该行时间则继续下一独立任务。不得把进度“完成”当实验成功。
- 状态为 BLOCKED_CACHE/DATA/IMPLEMENTATION/BUDGET/TARGET 时写准确缺口；方法公式冲突写 BLOCKED_DEFINITION，不改公式以获得正结果。不要反复问一般实现细节。
- CPU选点超时保存resume state（selected IDs、coverage/heap/PRNG、parent hash），恢复不能换采样序列。计算预算到顶时暂停队列并跑P99，不能删除旧失败记录。
- P99可以机械排序/生成下一阶段队列，不能宣布原创性、论文价值或自行启动未授权的阶段。

## 阶段1晋级的确定性排序

先丢弃不正确/不公平/缺必要对照者，再按S7的mean质量、尾部、LPIPS、资源或时间门槛判断。P09可用规定恢复probe门槛作为机制例外，阶段2在新增场景重复同一16候选probe（每run含在30分钟上限），阶段3才作统一1000步FT结论；不能用局部probe直接作论文质量结论。每个不同预算赛道先选其非支配解，合计最多6候选；若超额，优先机制证据更完整者，然后按“相对最强同成本控制的PSNR改善 + 0.1×资源改善比例”降序（资源改善比例取0..1），并列ID小者。这个分数仅排队，不是科学效应量；将全部Pareto表留给Astra，不隐藏被挤出的方案。

阶段2有≥2场景通过门槛后同规则选最多3；只有1场景时标泛化未验证，队列不自动启动阶段3。阶段3用3强对照：P01最佳简单规则、P02、P11最好的合格mask行（它若失败则P07；P07也失败则P03最佳，明示替换），同总优化预算；原论文全pipeline未复现的局限必须保留。

先来先占，同(scene、cap类型、cap值、参考hash、score规则)复用。P14–P20需要的新cap超过4个时：仍可做各自内部结构对照，但“same-byte优于剪枝”的结论标未验证；阶段1可凭明确机制与内部对照进入待补证队列，不正式晋级，阶段2从96run额度扣除补匹配后再决定。不得偷偷为每个cap增加两条正式评测。阶段2每场景、预算给出共同资源cap后冻结，便于复用。
